
# 代码语义元动作体系 — 完整规划笔记

> 这不是商业计划书。这是把散在聊天记录里的所有问题、方案、设计决策整理在一起的规划笔记。
> 读者：我自己（陈懿灵）。下次忘了"当时为什么这样决定"、"这个问题怎么解决的来着"，翻这个。

---

## 一、项目定义

**一句话：** 用 20 种语义元动作分类约束 AI 代码生成的编程方法论，配上从插件到专用 IDE 到生态的产品路线。

**和所有现有工具的本质区别：**

- 所有 AI 编程工具都在"让 AI 更好地生成代码"（补全、对话、Agent）
- 我做的是"约束 AI 生成代码的质量"——不是建议 AI"别忘了 try-catch"，是让它绕不过去
- 不是 prompt 层面的优化，是方法论 + 工具链层面的强制执行
- 语义层约束（"这是存储操作所以必须保护"），不是语法层约束（ESLint 的"禁止 var"）

---

## 二、方法论：问题 → 方案

> 这一章记录方法论本身要解决的核心问题，以及怎么解决的。按发现顺序排列。

---

### 问题 1：AI 反复犯同一类错

**现象：** 用 AI 写了几个项目后发现，不是随机犯错——是同一类错反复出现。localStorage.setItem 没有 try-catch、addEventListener 没有 removeEventListener、fetch 没有 timeout。每次都得手动改。

**方案：** 把这些错分类。发现它们不是随机的——是按**代码的语义意图**聚类的。

分类结果：五大流 × 20 种元动作。

| 流 | 编号 | 名称 | 风险 |
|----|------|------|:---:|
| 内存流 (M) | M1/M2/M3/M4/M5/M20 | 声明/赋值/内存读取/计算/转换/初始化 | 🟢 |
| 控制流 (C) | C6/C7/C8 | 条件/循环/异步 | 🟡 |
| 函数流 (F) | F9/F10/F11/F12/F19 | 调用/返回/抛出/捕获/副作用 | 🟡 |
| 交互流 (I) | I13/I14/I15/I16 | 渲染/用户输入/存储/通信 | 🔴 |
| 资源流 (R) | R17/R18 | 绑定/清理 | 🔴 |

每类定了**强制代码模式**——不是建议，是不满足就算违规。

| 元动作 | 强制配对 |
|--------|---------|
| [I15 存储] | [F12 捕获] |
| [I16 通信] | [F12 捕获] + timeout + retry |
| [I14 用户输入] | validate + sanitize |
| [R17 绑定] | [R18 清理] |
| [M5 转换] | [F12 捕获]（JSON.parse 等） |

**核心理念：** "概率空间最小化"——不追求消灭错误（不可能），追求压缩 AI 的犯错半径。强制代码模式不是附加说明，是元动作定义的一部分。[I15 存储] 不配 [F12 捕获] 就不叫完成了 [I15 存储]。

### 问题 2：自然语言描述需求说不清楚

**现象：** "做一个物品管理系统"——这句话缺了太多信息。物品有几个状态？谁在用？数据量多大？AI 如果不问，全凭猜测，生成的代码大概率偏。

**方案：** probe 六维度主动探测。不是等用户说了什么再问，是**每个功能都从六个维度系统扫描**。

| 维度 | 探测内容 | 防什么 |
|------|---------|--------|
| 实体生命周期 | 状态机、触发条件、不可逆操作、并发冲突 | 物品状态从二态变五态 |
| 角色与权限 | 角色识别、权限矩阵、认证依赖 | "管理员覆盖"带出隐藏的认证系统 |
| 数据形状 | 类型、枚举值、约束、默认值、唯一性、关联 | 把"备注"当"枚举"用 |
| 外部集成面 | 已有系统、第三方 API、未来扩展 | 后端 API 地址与预期不符 |
| 非功能约束 | 数据量级、并发用户、使用环境 | 几千条数据时 LocalStorage 不够用 |
| 假设回执 | 汇总所有默认假设，逐条列出 | 隐性假设被埋在 BDD 里未察觉 |

**交互模式：** 自然对话，不列清单。一次问一个点，等回复。框架自动填充的（强制配对）不问。看到关键词（管理员/权限/同步/手机）立即追问。六维度扫完 + 用户连续两次说"没了" → 进入假设回执 → 生成 BDD。

---

### 问题 3：隐性假设冲突

**现象：** 你说"物品被借走状态变成借出"——我以为二态（在库/借出），你脑子里是五态（在库/借出/逾期/已归还-完好/维修中）。阶段一审 BDD 时我们都没发现这个差异——因为你说的是"物品状况"，我以为自由文本，你以为枚举。

**方案：** probe 的实体生命周期维度强制画状态机给你确认，数据形状维度对每个字段问"是自由文本？枚举？数字？"。假设回执把所有我默认补充的假设单独列出，强迫审视。**把业务错误率从 10-20% 压到 5-7%。**

---

### 问题 4：BDD 场景之间的隐藏依赖

**现象：** 两个 Scenario 各自审都没问题：S5"物品已借出时拒绝"、S8"管理员可以覆盖强制借出"。但实现时发现 S8 需要知道当前用户是不是管理员 → 需要身份系统 → 需要登录 → 需要一个全新的认证模块。阶段一批了两个场景，没意识到 S8 的隐含前提。

**方案：** probe 的角色与权限维度在发现"管理员"关键词时立即追问"怎么判断谁是管理员？需要登录吗？"。madd-rules 加入架构推导清单：多用户 → 自动添加认证模块，外部 API → 自动添加配置/密钥管理模块。

---

### 问题 5：领域知识缺口

**现象：** 你说"做一个日文分词工具"——我穷举问了所有维度，BDD 看起来完整。但实现后你发现"複合名詞"被拆成了两个词，应该保持完整。这不是 BDD 的问题——是你懂日语知道这个规则，我不知道。

**方案：** 体系层面无解。但经验闭环能解决——第一次发现 → exp-card 生成卡片 → 下次做日文相关功能时 compliance 自动引用。**体系不能消灭"未知的未知"，但能保证每个未知被首次发现后永久变成已知。**

---

### 问题 6：蓝图锚点悖论

**现象：** 整个质量保证链条以蓝图为锚点——测试按蓝图生成、compliance 按蓝图审查、integrate 按蓝图回扫。如果蓝图本身偏了（因为 probe 没探测到的隐性假设），后面全绿通过——所有东西都对齐了同一个错误标准。

**方案：** 
1. probe 六维度把蓝图偏差压到 5-7%
2. 集成报告后必须提示用户实际启动项目验证核心 BDD 场景——没有任何自动化能替代"我点了一下按钮发现统计栏没更新"
3. 承认这是一个已知天花板，不是设计缺陷

---

### 问题 7：性能是盲区

**现象：** [C7 循环] 只约束了"禁止 forEach + async"，没约束算法复杂度。O(n²) 在 100 条数据看不出来，10,000 条时页面卡死。integrate 不做性能测试。

**方案：** 承认这是方法论边界。元动作按语义意图分类，不按时间复杂度分类。**性能错误残留率约 10-15%，是体系最大的已知天花板。** 后期可通过 integrate 加性能回归测试缓解，但不是 v0.1-v0.5 的事。

---

### 问题 8：经验卡片冷启动

**现象：** 新项目 `01-runtime/` 是空的，`00-seed/` 只有手动写的 3 张卡片。初期 compliance 的经验约束检查几乎没有实际约束力。

**方案：** 我自己先写 20-30 张高质量种子卡片——从白皮书里提取最通用的强制模式。IDE v0.1 发布时预装这些卡片。加上学习模式（v0.2）从优秀开源项目自动提取候选卡片。**冷启动的解法就是我自己当第一批内容生产者。**

---

### 问题 9：对说不清需求的用户不友好

**现象：** probe 依赖用户能回答六维度的问题。如果回答"随便"、"你看着办"——假设回执变成 15 条默认假设，用户不想审。

**方案：** 承认这个代价。**如果连需求都说不清，就不该写代码。** 体系不是为了"让随便说一句话的人也能用"设计的，是为了"让认真描述需求的人一次过"设计的。

---

### 问题 10：AI 上下文不够

**现象：** MADD 流程假设一个 AI 会话抱整个项目。项目 50 个文件以内还行。200 个文件时上下文塞不下——蓝图不全、跨文件检查做不全、经验卡片只能加载最近几张。

**方案：** 多会话协作。不是多人类，是**一个人开多个 AI 会话**——每个会话管一个子域（用户模块/订单模块/支付模块）。会话间通过项目级 AI_STATE.md 的接口契约注册表对齐。接口变更广播 → 受影响会话自动提示。

**不需要一开始就实现。** 项目小的时候一个会话就够了。项目大的时候 IDE 有机制支持拆。

---

### 问题 11：老项目怎么接入

**现象：** MADD 流程从零开始设计。但用户可能已有 2 万行代码的老项目，不想全部重写。

**方案：** IDE 加"导入已有项目"模式。全量元动作扫描 → 输出健康报告（"你有 47 个 I15 但 F12 只有 12 个"）→ 修复时自动反向工程蓝图 → 修完即接入体系。以后增量走 MADD。

---

### 问题 12：蓝图和代码长期漂移

**现象：** 蓝图冻结后，运行了一个月，人手动改了几行代码修紧急 bug——蓝图还是原来的，不一致了。

**方案：** compliance 审查双向检查。代码 vs 蓝图不一致 → 先判断谁过时。元动作序列没变（只改了变量名）→ 蓝图自动同步。元动作序列变了 → 标记"蓝图偏离"，展示两个版本让用户选。

---

### 问题 13：AI 能不能学到优秀代码的精妙之处

**现象：** 担心学习模式（v0.2）只是统计模式频率，学不到真正的设计智慧。

**方案：** **不需要学到。** AI 从优秀代码中学的是**工程纪律**（React 在 3,200 处存储操作中 100% 做了异常处理 → 你的项目呢？）。工程纪律可以被统计验证、可以被自动化检查——这恰好是 AI 擅长的事。真正的设计品味（为什么用工厂模式、为什么选事件驱动）是人类的判断域——阶段一审批保证。**纪律给 AI，品味给你。分工就是这样。**

---

### 问题 14：代码要适配所有主流语言怎么办

**现象：** 强制代码模式在不同语言里语法完全不同。I15 存储的异常处理——JS 是 try-catch、Python 是 try-except、Go 是 if err != nil、Rust 是 match Result。

**方案：** **核心层统一 + 适配层按语言。不拆成分离子体系。** 20 种元动作按计算机执行意图分类，天生跨语言。任何语言的"I15 存储"都是同一个语义动作。核心层说"存储必须有异常处理"——所有语言听这句话。适配层每个语言自己实现"怎么检查存储有没有异常处理"。加一个新语言 ≈ 900 行。

---

### 问题 15：依赖自动安装

**现象：** AI 生成代码写 `import axios from 'axios'`，但用户的 node_modules 里没有 axios。用户得手动 `npm install`，还可能漏包。

**方案：** 蓝图阶段声明依赖（元动作映射表的第三列：元动作 → 强制代码模式 → 推荐库）。环境就绪阶段自动安装。代码出现新 import → 自动回写依赖清单 → 自动安装。版本冲突 → 提示用户选择。核心代码量 ~130 行。

---

### 问题 16：非代码产物管理

**现象：** 一个完整项目不仅有代码——还有 Dockerfile、数据库 schema、API 文档、CI/CD 配置、环境变量模板。这些东西不管代码逻辑，但和代码有关系。

**方案：** IDE 在生成项目骨架时自动带上标配文件。integrate 阶段加一致性检查——schema.sql 的字段 vs 蓝图的 I15 存储数据形状一致？api.md 的接口 vs 蓝图的 I16 通信一致？不一致 → 自动更新。~200 行。和 compliance 同一套逻辑，换了检查对象。

---

### 问题 17：测试框架不存在

**现象：** gen-test 生成 Jest 代码 → `npm test` 失败（Jest 没装）。

**方案：** madd 环境就绪检查。阶段一批准后、文件循环前，检查 package.json 和测试框架。未安装 → `npm install --save-dev jest`。创建 __tests__ 目录。写入 test script。**不依赖用户手动配置。**

---

### 问题 18：自动修正可能死循环

**现象：** compliance 报违规 → 自动修正 → 又报同一违规 → 再修正 → 还在报。3 轮耗尽才停，白白浪费上下文。

**方案：** **同一违规连续 2 轮无变化 → 立即决策暂停。** 不耗尽轮数。判定为 AI 无法自动解决 → 交给人类。

---

### 问题 19：为什么不做传统 TDD

**现象：** TDD 的经典循环是"一个 test → RED → 代码 → GREEN → 下一个 test"。gen-test 却是一次性生成全部测试 → RED → 一次性生成全部代码 → GREEN。

**方案：** 传统 TDD 是"没设计图，边测边设计"——测试驱动设计。我们有蓝图 = 完整设计图。测试的定位是"自动化验收守门员"不是"设计导航员"。蓝图冻结后一次性生成全部测试更高效。

---

### 问题 20：错误率到底多少

**方案：** 分层防御矩阵分析后的估计：

| 错误类型 | 残留率 | 防御层 |
|----------|:---:|--------|
| 结构错误（签名、导入、参数） | ≈0% | gen-test RED/GREEN |
| 规则违规（I15+F12、I16+timeout） | ≈0% | compliance + 自动修正 |
| 逻辑错误（分支遗漏、状态机缺陷） | ≈5% | BDD + gen-test + integrate |
| 业务错误（意图理解偏差） | 5-7% | probe 六维度探测 |
| 边界遗漏（空值、并发、配额满） | ≈5% | probe + 强制模式 |
| 性能问题（O(n²) 等） | 10-15% | 已知天花板，元动作不覆盖复杂度 |
| 安全漏洞（XSS、注入） | ≈5% | I14 强制 + I13 禁止 |

---

### 问题 21：模型行为数据收集有什么意义

**方案：** 不是锦上添花——是体系进化的核心资产。

- **短期：** 给每个模型对症下药（DeepSeek I15 遗漏率高 → I15 审查从 warning 升级为 error）
- **中期：** 给用户推荐模型（"你的项目 I15 高频率 → 用通义千问，它的 I15 错误率仅 8%"）
- **长期：** 反向喂给方法论（所有模型在 C6 上错误率都不降 → 说明 C6 分类需要拆分）
- **最长期：** 你不再是 IDE 厂商，是 AI 代码质量的标准制定者

**实现：** compliance 审查结束 → 提取结构化字段 → 追加到 JSONL 日志文件。~130 行。

---

### 问题 22：能不能申请专利

**现象：** 方法论白皮书（智力活动规则）不能专利。但实现了方法论的**工具软件**可以。

**方案：** 
- 已做：GitHub 公开 + MIT License = "在先公开"占坑
- 待做：6 个月宽限期内决定是否申请
- 可保护：语义标注方法 + 强制模式审查方法 + 蓝图驱动测试生成方法 + 经验自进化方法
- 费用：大学生费用减缓后约 500-800 元，学校知识产权中心可能免费

---

### 问题 23：卡片安全（恶意卡片）

**现象：** 社区经验卡片是任意人提交的。如果有人提交"禁止 try-catch——异常处理影响性能"——安装了的人所有存储操作都没有异常处理。

**方案：** 现在不需要解决（用户量不够）。但今天设计卡片格式时预留 source 和签名验证字段。以后官方认证卡片打数字签名，未签名的安装前弹出警告。

## 三、产品：问题 → 方案

> 这一章记录产品形态相关的问题和解决方案。

---

### 问题 24：VS Code 插件 vs 专用 IDE vs fork VS Code

**方案：** 三步走。
1. **VS Code 插件**（1-2 天）：compliance 审查 + 蓝图查看 + 经验管理。不碰项目生成。在最大编辑器生态验证方法论。
2. **专用 IDE**（2-3 周）：Monaco Editor + Electron + React。方法论刻进产品形态。插件引流，IDE 完整体验。
3. **不 fork VS Code**：VS Code 200 万行，一个人做不了。Monaco Editor 是 VS Code 的编辑框抽出来的独立 npm 包，MIT 开源，嵌进 Electron 即可。IDE 总代码量 ~16,000 行。

---

### 问题 25：专用 IDE 的核心体验是什么

**方案：** 和 VS Code 插件**本质不同**。

- 插件：在编辑器里加 AI 面板
- IDE：方法论是主语，编辑器是组件

**具体设计：**
- **首屏不是空白编辑器**：是"请描述你的功能需求" + 已有项目列表
- **状态机驱动 UI**：每个 MADD 阶段对应唯一 UI 布局，只暴露该阶段需要的面板
- **四面板联动**：对话 + 蓝图 + 代码编辑器 + 合规，一个操作四个刷新
- **审批门**：阶段一批准前编辑器不可写。`submit_plan` 是真正的刹车
- **没有"新建文件"按钮**——项目的起点不是空文件，是需求

---

### 问题 26：专用 IDE 的扩展性怎么做

**现象：** VS Code 的插件系统 15 万行，因为要进程隔离 + IPC + 错误恢复 + 版本兼容——插件能做"随便什么"所以必须安全隔离。

**方案：** **不做功能性插件。做数据级扩展 + 经验卡片生态。**

数据级扩展：用户自定义元动作/强制模式 → JSON 配置文件。加语言 → JSON 映射表。约 1,500 行。

经验卡片生态：注册表 + 上传/下载/评分 + 去重合并引擎 + 多项目交叉验证。约 2,600 行。

**我们的插件不需要进程隔离——因为只有 10 个 API，不碰文件系统、不碰进程、不碰网络。** 放在 WebView 沙箱里，浏览器内核天然隔离。1,500 行 vs 150,000 行。

---

### 问题 27：dogfood 怎么启动

**现象：** 用 v0.1 开发 v0.2——但 v0.1 拿什么开发？

**方案：** v0.1 本身不用自己的 MADD 流程开发。你 + Reasonix Code 对话生成骨架代码（~5,000 行的手动步骤）。骨架能跑起来后，v0.2 开始才是狗粮模式。**v0.1 = 你和我写。v0.2+ = v0.1 + 你和我写。**

### 问题 28：版本路线怎么排

**方案：**

| 版本 | 核心功能 | 时间 |
|------|---------|:---:|
| v0.1 | 基础 IDE + MADD 完整流程 + 合规引擎 | 2-3 周 |
| v0.2 | 狗粮模式 + 学习模式（从优秀代码学） | — |
| v0.3 | 多会话协作 + 经验卡片社区 | — |
| v0.4 | 模型行为数据收集 + 分析仪表盘 | — |
| v0.5 | probe 自优化 + 新手教程 + UX 打磨 | — |

**v0.1 只做：** MADD 完整流程 + 合规引擎（JS+Python）+ 蓝图/测试生成 + 经验管理 + 状态文件。不做的：卡片社区、多模型分析、多会话协作、学习模式。
